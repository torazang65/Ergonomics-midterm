# 문제 3 답안 초안

## 1단계 공감과 관찰

10월 22일 저녁 집에서 Mac으로 과제·공부를 하던 중 친구에게 과제를 질문하려고 카카오톡 대화로 돌아가는 과정에서 불편을 체험했다. 터치패드에서 네 손가락을 위로 쓸어 창 개요를 열었으나 목표 대화를 바로 찾지 못했다. Dock에서 카카오톡을 열자 여러 창이 나타났고, 본인은 창을 하나씩 닫으며 원하는 친구의 창을 찾았다.

후속 확인에서는 **목록 창이 열려 있으면 다른 대화창을 닫지 않고 목록에서 상대를 선택해 접근할 수 있었다.** 반면 목록을 닫은 상태에서는 대화창들만 남았고, 본인이 사용한 목록 복원 경로는 **Dock 아이콘 우클릭 → Chats 또는 Friends 선택**이었다. 아래 첫 이미지에는 Chats 목록 1개와 대화창 3개가 함께 보이고, 두 번째 이미지의 캡처 영역에는 대화창들만 보인다. 세 번째 이미지에서 Friends·Chats 메뉴 항목을 확인할 수 있다. 이 경로가 유일한 방법이라고 단정하지 않는다.

이 사례의 페르소나는 **여러 학습 앱을 쓰다가 친구에게 질문하기 위해 특정 대화로 돌아가는 Mac 사용자 학생**이다. 본인 1명의 경험에 근거한 과업 중심 페르소나다. 핵심 페인 포인트는 목록의 열림·닫힘 상태에 따라 대화 탐색의 진입점이 달라지고, 목록 복원 경로를 별도로 찾아 실행해야 한다는 것이다. 창을 닫았던 행동은 실제 경험이지만 시스템이 요구하는 필수 절차는 아니다. 소요 시간·오선택 횟수는 측정하지 않았다.

## 2단계 문제 정의

선정 문제는 **학습 중 목표 대화로 돌아갈 때, 목록 상태에 따라 탐색 진입점을 다시 찾아야 하는 부담**이다. 이미 작동하는 목록 선택 기능을 인정한 상태에서 다음 원인 가설을 세웠다.

| 원인 후보 | 인간공학적 진단 |
|---|---|
| 현재 대화 화면에서 목록 복원 경로가 명시적으로 드러나지 않음 | 다른 상대를 찾으려는 목표와 현재 화면에 제시된 조작 정보 사이에 실행차가 생길 수 있다. 확인된 복원 경로가 Dock 문맥 메뉴에 있어 사용 중인 대화 화면을 벗어나야 한다. 「8장 콘트롤 보충.pdf」 PDF p.4의 실행차 정의에 근거한다. |
| 메뉴의 위치와 조작 순서를 알아야 복원 경로를 이용할 수 있음 | Dock 메뉴도 열면 항목을 보고 선택할 수 있지만, 먼저 어디에서 메뉴를 열어야 하는지 알아야 한다. 현재 화면에 의미 있는 제어를 드러내면 경로 기억에 대한 의존을 줄일 수 있다는 가설이다. 「2026 4장 보충.pdf」 PDF p.34, 53의 머릿속 지식과 외부 단서, 회상·재인의 구분을 적용한다. |
| 함께 써야 하는 목록과 대화가 화면에서 떨어져 있음 | 목표 대화로 돌아가려면 목록에서 상대를 고르고 대화창에서 이름을 확인해 질문을 써야 한다. 두 정보를 한 과업에 함께 쓰므로 처리 근접성이 높다. 그런데 목록은 별도 창으로 대화창들과 겹쳐 있고, 닫히면 진입점이 화면 밖 Dock 메뉴에만 남아 표시 근접성이 낮다. 근접 부합성 원리에서 '함께 처리하는데 떨어뜨려 배치'한 불일치에 해당한다. 반대로 지금 과업과 무관한 다른 대화창들이 같은 영역에 겹쳐 있는 것은 '따로 처리하는데 가까이 배치'해 섞여 헷갈리는 불일치로 볼 수 있다. 「6장 디스플레이 보충 2026.pdf」 PDF p.32. 슬라이드의 예는 값 비교와 조작 버튼 배치이므로, 탐색 목록과 대화 내용에 적용한 것은 이 원리를 넓힌 해석이다. |
| 같은 외형의 대화창들이 서로 혼동될 수 있음 | 캡처에서 카카오톡 대화창들은 같은 배경색, 같은 상단 아이콘 배치, 같은 말풍선·입력 영역 구성을 공유한다. 상대를 구별할 단서는 상단의 이름·프로필 영역뿐이다. 비슷한 외형의 항목은 하나의 묶음으로 지각되기 쉽고(「3장 보충 2026.pdf」 PDF p.71, 101의 유사성 원리), 묶음 안에서 특정 창을 구별하려면 세부를 보는 초점 처리가 필요하다(같은 자료 PDF p.89). 유사성은 재인 실패, 즉 혼동의 원인으로도 제시된다(「2026 4장 보충.pdf」 PDF p.53). |
| 개별 창을 직접 고를 때 겹침이 상대 식별을 방해할 수 있음 | 추가 캡처에서 뒤쪽 대화의 이름·프로필 일부가 앞 창에 가려져 있다. 위의 유일한 구별 단서마저 가려지면 상대를 확인하기 어려울 수 있다. 「3장 보충 2026.pdf」 PDF p.83, 95, 97의 선택적 주의와 시각 탐색에 연결된다. |
| 조작할 때마다 목표에 도달했는지 다시 판단해야 함 | 처음에 창을 하나씩 닫으며 찾았을 때는 닫을 때마다 앞에 남은 창이 목표 상대인지 이름으로 다시 판단해야 했다. 실행 뒤 결과가 목적과 얼마나 차이 나는지를 판단하는 평가차가 매번 생기며, 위의 유사성·가림이 이 판단을 어렵게 할 수 있다. 「8장 콘트롤 보충.pdf」 PDF p.4의 평가차 정의에 근거한다. |

사용자가 경로를 잊었거나 잘못된 심성모형을 가졌다는 사실은 확인되지 않았다. 창을 잘못 고른 횟수나 판단에 걸린 시간, 시선 이동량도 기록하지 않았다. 가려진 대화가 최초 과제 질문의 목표였는지도 미확인이다. 따라서 원인과 개선 효과를 검증된 결과로 표현하지 않는다.

## 3단계 아이디어 도출

**어떻게 하면 목록 창이 열려 있든 닫혀 있든 학생이 현재 대화 화면에서 목표 대화를 찾는 경로를 쉽게 발견하고 실행할 수 있을까?**

| 대안 | 기대 효과 | 새 부담과 한계 |
|---|---|---|
| A 목록·내용 통합 창 | 탐색 목록과 대화 내용을 같은 창에 제시해 진입점을 유지한다. | 창 관리 구조와 기존 사용 방식의 변경이 크고 동시 비교가 불편해질 수 있다. |
| B 대화창 상단의 대화목록 버튼 | 닫힌 목록을 복원하거나 가려진 목록을 전면에 표시해 기존 목록 선택 경로에 연결한다. | 버튼 공간과 목록 상태 처리가 필요하며 창 겹침 자체는 남는다. |
| C 개별 창 식별 강화 | 큰 상대 이름·프로필로 창을 직접 고를 때 구별을 돕는다. | 목록이 닫힌 상태의 복원 경로는 그대로 남는다. |
| D 기존 Dock 메뉴 경로 안내 | 기존 기능으로 목록을 복원하는 방법을 알린다. | 현재 화면을 벗어나 메뉴를 찾아야 하고 안내한 절차를 기억해야 할 수 있다. |

**B를 프로토타입으로 선택한다.** 기존 목록 선택이 작동한다는 점을 활용하면서, 추가 자료에서 확인한 목록 복원 진입점에 직접 대응하기 때문이다. A의 전면적인 창 구조 변경보다 수정 범위를 좁히고 기존 독립 창 사용도 유지한다. 이 선택은 관찰에 따른 설계 판단이며 A보다 성능이 우수하다는 실험 결과는 아니다.

비교 자료인 인터넷 WhatsApp 이미지에서는 목록과 내용이 함께 배치되어 있고, 직접 캡처한 Discord 서버·채널 화면에서는 탐색 영역과 메시지 영역이 구분된다. 이 배치들은 대화를 찾는 진입점을 화면에 드러내는 참고가 된다. 다만 WhatsApp 이미지는 원래 출처와 실제 구현이 미확인이고, Discord는 개인 대화 과업과 다르므로 속도·정확도나 Dock 동작의 비교 근거로 쓰지 않는다(「WhatsappUI.png」, 「discordUI.png」).

## 4단계 프로토타입

각 대화창 상단의 같은 위치에 **대화목록** 문자 버튼을 둔다. 친구 목록과 구분해 Chats에 해당하는 대화 목록으로 연결한다.

![대화목록 복귀 버튼 제안](/Users/sukhosong/Code/Ergonomics%20midterm/output/q3-list-return-prototype.png)

1. 목록이 닫혀 있으면 목록 창을 복원하고, 열려 가려져 있으면 기존 목록 하나만 전면에 표시한다. 목록 창을 중복 생성하거나 모든 대화창을 함께 앞으로 가져오지 않도록 설계한다.
2. 사용자가 목록에서 상대를 선택하면 이미 열린 해당 대화창을 앞으로 가져온다. 목록 선택이라는 기존 기능을 이용하고, 상단 이름으로 목표 상대가 맞는지 확인하게 한다.
3. 목록을 다시 닫아도 각 대화창의 버튼은 남긴다. 다른 대화창을 닫거나 채팅방에서 나가지 않고 목록에 접근하도록 한다. 작성 중인 초안도 유지한다.
4. 조작 결과를 바로 확인할 수 있게 한다. 버튼을 누르면 목록이 전면에 나타나고, 목록에서 지금 대화 중인 항목은 '현재 대화', 나머지는 '이 대화로 이동'으로 표시한다. 상대를 고르면 대화창 상단 이름이 바뀐다. 창을 하나씩 닫으며 매번 목표인지 판단하던 방식 대신, 한 번의 선택과 이름 확인으로 결과를 평가하게 해 평가차를 줄이려는 설계다(「8장 콘트롤 보충.pdf」 PDF p.4).

이 버튼은 현재 화면에서 목적에 맞는 조작을 선택하게 해 실행차를 줄이려는 설계다. 함께 쓰는 목록으로 가는 진입점을 대화창 안에 두어 표시 근접성을 높이고, 이를 통해 근접 부합성의 불일치를 줄이려 한다(「6장 디스플레이 보충 2026.pdf」 PDF p.32). 비슷하게 생긴 창들 사이에서 상대를 골라야 하는 대신 이름이 나열된 목록에서 고르게 해 유사성에 의한 혼동도 줄일 것으로 기대한다. 의미 있는 문자 단서를 드러내 Dock 메뉴 위치와 순서에 대한 기억 의존도 줄일 것으로 기대한다. 다만 목록 창과 대화창은 여전히 별도 창이므로 근접성을 가장 크게 높이는 것은 A안이며, B안은 기존 독립 창 사용을 유지하는 대신 그 일부만 개선한다. 현재 모형은 같은 화면 안의 모의 창으로 버튼·목록 복원·상대 선택을 표현하며, 실제 카카오톡이나 OS의 창 전면화는 구현하지 않았다.

## 5단계 테스트 계획

테스트는 미수행이다. 기존 구조와 B를 같은 충실도의 모형으로 비교하고 **목록 열림·닫힘 조건을 각각 포함**한다. 기존 조건에서도 목록에서 바로 상대를 선택하는 방법과 Dock 우클릭 메뉴 등 확인된 경로를 허용하며 창 닫기를 강제하지 않는다. 상대 정보, 대화 수, 창 크기·가림과 화면 조건은 맞춘다.

버튼이나 기존 경로를 알려 주기 전의 첫 탐색과, 경로를 익힌 뒤의 반복 사용을 구분한다. 목표 대화 도달 여부·시간·오선택과 목록 복원 경로를 찾는 행동을 평가한다. 정확도와 완료율을 유지하며 복귀 부담을 줄이는지, 목록이 이미 열린 경우를 더 불편하게 만들지 않는지도 확인한다. 현재 모형만으로는 Dock을 포함한 전체 복귀 시간을 비교할 수 없어 비교 모형 준비 전에는 버튼 발견과 목록 복원의 형성 평가로 한정한다. 본인의 결과만 있으면 1인 예비 평가로 해석한다(「2장 보충 인간공학 연구방법론.pdf」 PDF p.22-23, 32).
