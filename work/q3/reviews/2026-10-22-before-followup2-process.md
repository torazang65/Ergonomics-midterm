## 1단계 공감과 관찰

과업 중심 페르소나는 집에서 Mac으로 과제·공부를 하다가 친구에게 질문하기 위해 특정 카카오톡 대화로 돌아가는 학생이다. 사용자 본인 1명의 사례에 한정한다. 나이·전공·숙련도·감정 점수·반복 빈도는 추가하지 않는다.

| 조건 | 확인된 화면·행동 | 과업상 의미 |
|---|---|---|
| 최초 경험 | 창 개요에서 목표를 못 찾음 → Dock에서 앱 활성화 → 여러 창 표시 → 사용자는 창을 닫으며 탐색 | 이 사용자가 취한 우회 행동. 창 닫기를 필수 절차로 쓰지 않음 |
| 목록 열림 | 목록과 대화창들이 겹쳐 보임. 사용자 확인상 목록에서 상대 선택으로 다른 창을 닫지 않고 접근 가능 | 기존에 작동하는 경로로 인정하고 개선안·테스트의 기준에 포함 |
| 목록 닫힘 | 캡처 영역에 대화창들만 보임. 사용자는 Dock 우클릭 → Friends/Chats로 목록 복원 | 대화 화면과 목록 복원 진입점 사이의 이동·경로 지식이 필요 |

단일 문제 범위는 학습 중 목표 대화 복귀다. 채팅 목록의 채널·광고 분류 문제는 포함하지 않는다. 소요 시간·오선택·인지 부하의 실측값은 없다.

## 2단계 문제 정의

현재 문제 정의: 목록이 열려 있으면 대화 선택이 가능하지만, 닫히면 사용자가 알고 있는 목록 복원 경로를 별도로 실행해야 한다. 여러 독립 창을 직접 구별하거나 목록 복원 경로를 찾는 부담을 줄일 필요가 있다.

| 원인 가설 | 근거와 적용할 원리 | 원본 PDF 페이지 | 한계 |
|---|---|---|---|
| 현재 대화 화면에서 목록 복원 방법이 명시적으로 드러나지 않음 | 목표는 다른 대화 찾기인데 확인된 복원 제어는 Dock 문맥 메뉴에 있음. 목적과 현재 제시된 조작 정보 사이의 실행차로 해석 | 「8장 콘트롤 보충.pdf」 p.4 | 다른 앱 메뉴·단축키·상단 메뉴의 기능은 미확인. 기능 부재나 잘못된 심성모형으로 단정하지 않음 |
| 복원 경로를 이용하려면 메뉴 위치·절차를 알아야 함 | 대화 화면에 '대화목록'을 드러내 머릿속 절차 지식에 덜 의존하고 보이는 단서에서 선택하도록 지원 | 「2026 4장 보충.pdf」 p.34, 53 | Dock 메뉴도 열면 재인을 지원함. 사용자가 경로를 잊었다거나 작업기억 용량을 초과했다는 주장은 하지 않음 |
| 함께 써야 하는 목록과 대화가 화면에서 떨어져 있음 | 목표 대화 복귀에는 목록 선택과 대화 확인이 함께 필요(처리 근접성 높음). 목록은 별도 창으로 겹치거나 닫히면 Dock 메뉴에만 있음(표시 근접성 낮음). 강의 표의 '함께 처리 + 떨어뜨려 배치' 불일치. 과업과 무관한 다른 대화창이 같은 영역에 겹친 것은 '따로 처리 + 가까이 배치' 불일치로 해석 | 「6장 디스플레이 보충 2026.pdf」 p.32 | 슬라이드 예시는 값 비교·버튼 배치. 탐색 목록에 적용한 것은 해석적 확장. 시선 이동·비교 시간 미측정 |
| 같은 외형의 대화창들이 서로 혼동될 수 있음 | 캡처에서 대화창들이 배경색·상단 아이콘·말풍선 구성을 공유하고 구별 단서는 상단 이름·프로필에 집중. 유사성에 따른 묶음 지각, 개별 구별에 초점 처리 필요, 유사성에 의한 재인 혼동 | 「3장 보충 2026.pdf」 p.71, 89, 101; 「2026 4장 보충.pdf」 p.53 | '창을 고르기 어려웠다'는 자기보고의 원인 가설. 오선택 횟수·혼동 사례 미기록 |
| 창을 직접 고를 때 가림이 식별에 영향 가능 | 후속 이미지에서 뒤쪽 이름·프로필 일부가 가려짐. 시각 탐색·선택적 주의의 분석 대상 | 「3장 보충 2026.pdf」 p.83, 95, 97 | 가려진 대화가 최초 목표였는지와 탐색 지연량은 미확인 |
| 조작 뒤 목표에 도달했는지 판단하는 부담 | 창을 하나씩 닫은 최초 방식에서는 매번 앞에 남은 창이 목표인지 이름으로 다시 판단해야 함. 유사성·가림이 이 평가를 어렵게 할 수 있음. 선택안에서도 버튼·선택 결과가 즉시 보여야 새 평가차를 만들지 않음 | 「8장 콘트롤 보충.pdf」 p.4 | 판단 시간·오판 미기록. 원인 연결은 가설이며 설계 기준으로 주로 사용 |

각 인용 페이지는 원문 PDF에서 추출해 확인했고, 그림 중심인 6장 p.32와 3장 p.71은 렌더링해 표의 칸과 그림을 확인했다. 게슈탈트 그룹화가 전혀 없다는 주장은 하지 않는다. 근접 부합성은 시험지 p.10이 예로 든 원리이며, 위 표처럼 적용 범위를 해석으로 표시해 사용한다.

## 3단계 아이디어 도출과 선택

HMW: 어떻게 하면 목록 창이 열려 있든 닫혀 있든 학생이 현재 대화 화면에서 목표 대화를 찾는 경로를 쉽게 발견하고 실행할 수 있을까?

| 대안 | 기대 효과 | 적용 범위·새 부담 | 검증 |
|---|---|---|---|
| A 통합 대화 모드 | 목록·내용을 함께 보여 탐색 진입점 유지 | 창 관리 구조와 기존 사용 방식 변화, 동시 비교의 불편. 목록을 닫는 제어 설계도 필요 | 두 목록 상태에서 전체 복귀 과업 비교 |
| B 각 대화창의 대화목록 버튼 | 닫힌 목록 복원·가려진 목록 전면 표시를 현재 화면에서 실행 | 모든 대화창에 버튼·목록 상태 처리 필요. 창 겹침 자체는 남음 | 첫 발견, 목록 복원·상대 선택, 열린 목록에서의 회귀 불편 평가 |
| C 개별 창 제목·프로필 강화 | 직접 창을 고를 때 식별 지원 | 닫힌 목록의 접근 경로는 그대로임 | 같은 창 수·가림 조건에서 상대 탐지 비교 |
| D 기존 Dock 메뉴 경로 안내 | 제품 구조 변경 없이 기존 목록을 이용 | 사용 중 화면에서 벗어나 메뉴 경로를 찾아야 함. 안내 기억 부담 가능성 | 안내 전후와 B를 비교하되 학습 효과 구분 |

근접 부합성 측면에서 A는 목록과 내용을 한 창에 두어 표시 근접성을 가장 크게 높이고, B는 목록으로 가는 진입점을 대화창 안에 두어 거리를 줄인다. C는 유사성 혼동에, D는 기억 의존에 대응하지만 표시 거리는 그대로다.

현재 선택은 B다. 이미 작동하는 목록 선택 기능을 활용하면서 새 자료가 보여 준 목록 복원 진입점에 직접 대응한다. A보다 실측 성능이 좋다는 결론은 아니다. A는 대안으로 남기고 이전 모형도 보존한다.

WhatsApp 인터넷 참고 이미지의 목록·내용 병렬 배치와 Discord 직접 캡처의 탐색·내용 영역 구분은 진입점을 보이는 곳에 둔 배치의 참고다. 이 자료로 Dock 동작·상태 보존·성능을 추정하지 않는다. 자세한 비교는 work/q3/pc-ui-comparison.md에 있다.

## 4단계 프로토타입

선택안은 각 대화창 상단의 문자 버튼 '대화목록'이다. 친구 목록과 구별해 Chats에 해당하는 대화 목록을 연결한다.

1. 닫혀 있으면 대화 목록 창을 복원하고, 열려 가려져 있으면 기존 목록 하나만 전면 표시한다. 중복 목록을 만들거나 모든 대화창을 함께 올리지 않는 동작을 제안한다.
2. 목록에서 상대를 선택하면 기존에 열린 대상 대화창을 앞으로 가져온다. 기존 목록 선택이 가능하다는 확인을 활용하며 버튼에서 이 경로로 이어지는 부분은 구현 요구다.
3. 목록을 다시 닫아도 각 대화창 상단 버튼은 남긴다. 대화창을 닫거나 나갈 필요가 없게 한다. 대화·초안 상태 유지가 요구된다.
4. 버튼의 위치·이름을 모든 대화창에서 일치시키고, 선택 후 대화 상단 이름으로 결과를 확인하게 한다. 목록에는 현재 대화 항목을 '현재 대화'로 표시한다. 버튼·선택의 결과가 즉시 보이게 해 평가차를 줄이려는 요구다(「8장 콘트롤 보충.pdf」 p.4). 현재 모형은 상단 이름 갱신과 목록의 '현재 대화'/'이 대화로 이동' 표시를 구현했다. 오류 메시지나 실제 전송 기능은 모형에 추가하지 않는다.

모형: work/q3/kakao-list-return.html. 그림: output/q3-list-return-prototype.png. 같은 화면 안의 모의 창으로 목록 표시·닫기·복원·상대 선택·초안 유지 동작을 보여 준다. 실제 OS 창 전면화·카카오톡 수정·Dock 제어는 구현하지 않는다. 이전 A 모형은 work/q3/kakao-return.html 및 output/q3-prototype.png로 남긴다.

## 5단계 테스트 계획

미수행 계획이다. 시험지 PDF p.9는 5단계를 명시하나 답안 칸은 p.11의 프로토타입까지다. 추가 공지로 실수행을 요구한다면 확인한다. 수행하지 않은 결과를 작성하지 않는다.

- 독립변수: 기존 경로와 B. 목록 열림/닫힘을 각각 과업 조건으로 둔다.
- 비교 기준: 기존 목록이 열린 조건에서는 실제 목록 선택 경로를 허용한다. 닫힌 조건에서는 Dock 우클릭→Chats와 실제 확인된 다른 경로를 허용한다. 창 닫기를 강제하지 않는다.
- 과업: 다른 앱으로 학습 중 지시받은 상대의 대화를 열고 이름을 확인한다. 전체 시간은 학습 화면의 지시부터 확인 완료까지다. 현재 모형만으로 이 전체 시간을 비교하지 않는다.
- 통제: 다른 앱·대화의 수, 상대 정보·내용, 창 크기·가림, 해상도·배율을 조건 간 맞춘다. 목록 열림/닫힘에 따른 구조 차이만 계획대로 둔다.
- 지표: 완료 여부, 전체 시간, 잘못된 상대 선택, 목록을 여는 경로를 발견하기까지의 행동·도움 요청. 닫기 수는 보조 지표다.
- 발견 가능성: 버튼·Dock 경로를 알려 주기 전의 첫 탐색과, 경로를 익힌 뒤의 반복 효율을 구분한다. 첫 탐색에서 배운 기능을 반복해서 '처음 발견'한 자료로 세지 않는다. 사용자 본인은 Dock 경로를 이미 알고 있다는 점을 기록한다.
- 후속 정량 비교 전에 같은 충실도의 기존 경로 모형을 준비한다. 그 전에는 현재 모형을 이용한 버튼 발견·목록 복원·상대 선택의 형성 평가만 가능하다. 같은 참가자의 조건 순서·연습량·시행·중단 기준은 실행 전에 정한다.
- 판단: 완료율·선택 정확도가 낮아지지 않으면서 시간·복원 경로 탐색 부담이 줄어드는지 본다. 목록이 이미 열린 조건을 불편하게 만들지 않는지도 확인한다. 한 사람의 결과는 예비 평가로 한정한다.

새 세 이미지와 자기보고로 목록 상태·확인된 Dock 경로·기존 목록 접근 가능성은 보강됐다. 다른 메뉴·단축키나 대화창 메뉴의 목록 복원 기능 유무, 실제 앱·OS 버전의 관찰 당시 동일 여부, 비교 DM 화면·WhatsApp 원래 URL, 실제 사용자 평가는 여전히 확인 필요다. 추가 자료는 이 부분이 결론을 바꿀 때만 요청한다.
