# 문제 3 답안 초안

## 1단계 공감과 관찰

10월 22일 저녁 집에서 Mac으로 과제·공부를 하던 중(학습 현장), 친구에게 과제를 질문하려고 카카오톡 대화로 돌아가는 과정에서 불편을 체험했다. 터치패드에서 네 손가락을 위로 쓸어 창 개요를 열었으나 여러 앱 창 사이에서 목표 대화를 바로 찾지 못했다(그림 1). Dock에서 카카오톡을 열자 창 4개가 한꺼번에 나타났고, **원하는 친구의 창을 찾기 위해 창을 하나씩 닫아야 했다.** 이때 대화 목록 창은 열려 있었지만 다른 창들에 가려져 보이지 않았다.

후속 확인에서 목록이 보이면 다른 창을 닫지 않고 목록에서 상대를 골라 접근할 수 있음을 확인했다(그림 2). 목록을 닫으면 대화창들만 남고, 본인은 Dock 아이콘 우클릭 → Chats로 목록을 다시 연다(그림 3). 따라서 창 닫기는 시스템이 요구하는 절차가 아니라, 목록이 가려진 상태에서 택한 우회 행동이다.

페르소나는 **여러 앱 창을 동시에 띄워 두고 터치패드 창 개요로 전환하며 공부하다가, 친구에게 질문하려고 특정 대화로 돌아가는 Mac 사용자 학생**이다. 본인 1명의 경험에 근거한 과업 중심 페르소나다. 핵심 페인 포인트는 **열려 있는 대화 목록이 다른 창에 가려져 보이지 않아, 목표 대화를 찾으려고 창을 하나씩 닫아야 했다는 것**이다. 소요 시간·오선택 횟수는 측정하지 않았다.

## 2단계 문제 정의

선정 문제는 **학습 중 목표 대화로 돌아갈 때, 대화 목록이라는 진입점이 열려 있어도 다른 창에 가려져 쓰이지 못하고 개별 창을 하나씩 닫는 우회로를 택하게 되는 부담**이다.

| 원인 | 인간공학적 진단 |
|---|---|
| 목표에 필요한 목록이 현재 화면에 나와 있지 않음 | 실행차는 사용자의 목적과 시스템 이미지에 현재 나와 있는 기능·정보의 차이다(「8장 콘트롤 보충.pdf」 PDF p.4). 다른 대화를 찾는 목적에 맞는 기능인 목록이 가려져 화면에 없었다. 목록이 열려 있다는 사실과 위치를 머릿속 지식으로 떠올려야 하고, 닫힌 경우에는 Dock 메뉴 절차까지 알아야 한다. 화면의 단서로 고르는 재인 대신 회상에 의존하게 되는 상태다(「2026 4장 보충.pdf」 PDF p.34, 53). |
| 가림으로 탐색 정보가 시야에서 빠짐 | 그림 2처럼 창이 겹치면 목록 일부와 대화 상대의 이름·프로필이 가려진다. 선택적 주의와 시각 탐색은 보이는 정보를 대상으로 하므로, 가려진 목록은 탐색 후보에서 빠질 수 있다(「3장 보충 2026.pdf」 PDF p.83, 95, 97). |
| 창 개요에서 대화창들이 비슷하게 보임 | 그림 1의 썸네일 크기에서는 카카오톡 창들의 같은 배경색과 배치가 두드러지고, 구별의 주된 단서인 상대 이름은 읽기 어렵다. 비슷한 외형의 항목은 하나의 묶음으로 지각되기 쉽고, 그 안에서 특정 창을 구별하려면 세부를 보는 초점 처리가 필요하다(「3장 보충 2026.pdf」 PDF p.71, 89, 101). 기억 인출 측면에서도 유사성은 재인 실패의 원인으로 제시된다(「2026 4장 보충.pdf」 PDF p.53). |
| (보조) 목록과 대화가 별도 창으로 분리됨 | 같은 과업에 쓰이는 목록과 대화가 서로 가릴 수 있는 별도 창이라는 점은 근접 부합성과 관련된다(「6장 디스플레이 보충 2026.pdf」 PDF p.32). 다만 원리의 예는 두 정보의 비교·통합이므로, 목록에서 대화로 가는 순차 이동에 적용한 것은 해석적 확장이다. |

대화창 메뉴나 단축키에 목록을 여는 기능이 있는지는 확인하지 못했다. 있다면 문제는 경로가 없는 것이 아니라 잘 발견되지 않는 것이다. 사용자가 경로를 잊었거나 잘못된 심성모형을 가졌다는 사실도 확인되지 않았으므로, 원인과 개선 효과를 검증된 결과로 표현하지 않는다.

## 3단계 아이디어 도출

**어떻게 하면 목록이 다른 창에 가려지거나 닫혀 있어도, 학생이 지금 보고 있는 대화창에서 바로 목록을 불러내 목표 대화로 돌아갈 수 있을까?**

| 대안 | 대응하는 원인·인지적 한계 | 새 부담과 한계 |
|---|---|---|
| A 목록·내용 통합 창 | 근접 부합성, 가림(목록이 내용과 한 창에 있음) | 창 관리 구조와 기존 사용 방식의 변경이 크고 동시 비교가 불편해질 수 있다. |
| B 대화창 상단의 대화목록 버튼 | 실행차·기억 의존, 가림(가려진 목록만 앞으로) | 버튼 공간과 목록 상태 처리가 필요하다. 창 개요 단계와 창끼리의 겹침은 남는다. |
| C 개별 창 식별 강화 | 유사성(창 개요·겹친 창에서 이름·프로필을 크게) | 가려지거나 닫힌 목록 문제는 그대로 남는다. |
| D 기존 Dock 메뉴 경로 안내 | 기억 의존 | 화면 밖 메뉴로 가야 하고 안내한 절차를 기억해야 한다. |

**B를 프로토타입으로 선택하고 C를 보조안으로 둔다.** 불편 당시 목록은 이미 열려 있었으므로, 새 구조를 만드는 것보다 가려진 기존 목록을 지금 보는 대화창에서 바로 불러내는 것이 확인된 문제에 가장 직접 대응한다. A보다 변경 범위가 좁고 기존 독립 창 사용도 유지한다. 창 개요 단계의 유사성은 B가 다루지 못하므로 C로 보완한다. 이는 효과·실현 가능성·새 부담을 고려한 설계 판단이며, A보다 성능이 우수하다는 실험 결과는 아니다.

## 4단계 프로토타입

각 대화창 상단의 같은 위치에 **대화목록** 문자 버튼을 둔다.

![그림 4. 대화목록 버튼 제안 모형: 가려진 목록을 버튼으로 앞으로 가져와 상대를 고르는 과정(모의 화면·가상 대화)](q3-list-return-prototype.png)

1. 목록이 열려 있으나 다른 창에 가려져 있으면 그 목록 하나만 앞으로 가져오고, 닫혀 있으면 복원한다. 목록 창을 중복 생성하지 않는다.
2. 목록에서 상대를 고르면 그 상대의 대화창이 앞으로 온다. 목록에는 지금 대화 중인 항목을 '현재 대화', 나머지를 '이 대화로 이동'으로 표시하고, 선택 후에는 대화창 상단 이름으로 목표 상대인지 바로 확인하게 한다. 조작의 결과를 즉시 보여 평가차를 만들지 않으려는 설계다(「8장 콘트롤 보충.pdf」 PDF p.4).
3. 다른 대화창을 닫거나 채팅방에서 나가지 않고 목록에 접근하게 한다. Dock 메뉴 등 기존 경로는 그대로 둔다.

이 버튼은 목적에 맞는 기능을 지금 보는 화면에 드러내 실행차를 줄이고, 목록의 위치나 Dock 절차를 떠올리는 대신 보이는 문자 단서에서 고르게 하려는 설계다. 비슷한 창들 사이에서 고르는 대신 이름이 나열된 목록에서 고르게 되는 효과도 기대한다. 그림 4는 모의 화면에서 ① 목록이 다른 창들 뒤에 가려진 상태, ② '친구 나' 창의 버튼으로 목록 하나만 앞으로 가져온 상태, ③ 목록에서 '친구 가'를 골라 그 대화창이 앞으로 온 상태를 보여 준다. 창 배치와 다른 앱 창은 예시이며, 실제 카카오톡이나 macOS의 창 동작을 구현한 것은 아니다.

## 5단계 테스트 계획

테스트는 미수행이다. 창 개요에서 시작해 지시받은 상대의 대화를 여는 과업으로, 목록이 열려 있으나 가려진 조건과 닫힌 조건에서 기존 구조와 B를 비교한다. 기존 조건에서는 목록 선택·Dock 메뉴·창 닫기 등 모든 경로를 허용하고, 완료 여부·시간·오선택과 목록을 찾기까지의 행동을 본다. 버튼의 첫 발견은 참가자당 한 번만 측정되므로 참가자 간 비교가 필요하며, 경로와 설계 의도를 아는 본인은 그 대상이 될 수 없다(「2장 보충 인간공학 연구방법론.pdf」 PDF p.22-23, 32).
