## 1단계 공감과 관찰

과업 중심 페르소나는 집에서 Mac으로 과제·공부를 하며 여러 앱 창을 동시에 띄워 두고(Kakaotalk Reference.png), 터치패드 창 개요로 창을 전환하는(자기보고) 학생이다. 친구에게 과제를 묻기 위해 특정 카카오톡 대화로 돌아가려 한다. 사용자 본인 1명의 사례에 한정하며 나이·전공·숙련도·감정 점수·빈도는 추가하지 않는다. 집에서의 공부는 시험지 PDF p.9의 "학생들의 학습과 연구 현장"에 해당하는 것으로 연결한다.

| 조건 | 확인된 화면·행동 | 과업상 의미 |
|---|---|---|
| 불편 장면 | 창 개요에서 목표를 못 찾음 → Dock에서 앱 활성화 → 창 4개가 한꺼번에 뜸 → 창을 하나씩 닫으며 탐색. 당시 목록 창은 열려 있었으나 다른 창에 가려짐 | 쓸 수 있는 진입점이 있었지만 보이지 않아 우회 행동을 택함 |
| 목록 열림(재현) | 목록과 대화창들이 겹치고 목록 일부·뒤쪽 대화 이름이 가려짐. 목록에서 상대 선택으로 다른 창을 닫지 않고 접근 가능 | 목록이 보이면 작동하는 경로. 개선안이 활용할 기존 기능 |
| 목록 닫힘(확장) | 캡처 영역에 대화창들만 보임. Dock 우클릭 → Friends/Chats로 복원 | 화면 밖 메뉴와 절차 지식이 필요 |

페인 포인트는 사용자가 겪은 일로 쓴다. 원하는 친구의 창을 바로 찾지 못해 창을 하나씩 닫아야 했다. 소요 시간·오선택·인지 부하의 실측값은 없다. 채널·광고 분류 문제는 포함하지 않는다.

## 2단계 문제 정의

현재 문제 정의: 학습 중 목표 대화로 돌아갈 때, 대화 목록이라는 진입점이 열려 있어도 다른 창에 가려져 쓰이지 못하고 사용자가 개별 창을 하나씩 닫는 우회로를 택하게 되는 부담.

| 원인 가설 | 근거와 적용할 원리 | 원본 PDF 페이지 | 한계 |
|---|---|---|---|
| 목표에 필요한 목록이 현재 화면에 나와 있지 않음 | 실행차 정의("목적과 시스템 이미지에 현재 나와있는 기능 또는 정보의 차이")에 해당. 목록이 열려 있다는 사실과 위치를 머릿속 지식으로 떠올려야 함. 닫힌 경우 Dock 절차 지식까지 필요 | 「8장 콘트롤 보충.pdf」 p.4; 「2026 4장 보충.pdf」 p.34, 53 | 대화창 ≡ 메뉴·메뉴 막대·단축키의 목록 열기 기능 미확인. 망각·잘못된 심성모형 단정 안 함 |
| 가림으로 탐색 정보가 시야에서 빠짐 | 재현 화면에서 목록 일부와 뒤쪽 대화 이름·프로필이 가려짐. 선택적 주의·시각 탐색은 보이는 정보에 한정 | 「3장 보충 2026.pdf」 p.83, 95, 97 | 불편 당시 화면 캡처 없음. 탐색 시간·시선 미측정 |
| 창 개요에서 대화창들이 비슷하게 보임 | 썸네일 크기에서 같은 배경·배치가 두드러지고 이름은 읽기 어려움. 유사성에 따른 묶음 지각, 개별 구별에 초점 처리 필요. 기억 인출 측면의 유사성 혼동 | 「3장 보충 2026.pdf」 p.71, 89, 101; 「2026 4장 보충.pdf」 p.53 | 캡처가 불편 시점 화면인지 확인 필요. 실제 크기 창에는 인원수·프로필·배너 등 다른 단서도 있음 |
| (보조) 목록과 대화가 별도 창으로 분리됨 | 같은 과업에 쓰이는 목록과 대화가 서로 가릴 수 있는 별도 창. 근접 부합성과 관련 | 「6장 디스플레이 보충 2026.pdf」 p.32 | 원문의 처리 근접성 예는 비교·통합. 순차 이동에 적용한 것은 해석적 확장. 직접 대응은 A |

평가차(「8장 콘트롤 보충.pdf」 p.4)는 창을 닫을 때마다 목표인지 다시 확인했을 것이라는 추정에만 연결되며, 판단이 어려웠다는 보고가 없으므로 원인 표에 넣지 않고 4단계 설계 기준으로 쓴다.

각 인용 페이지는 원문 PDF에서 추출해 확인했고, 그림 중심인 6장 p.32와 3장 p.71은 렌더링해 확인했다.

## 3단계 아이디어 도출과 선택

HMW: 어떻게 하면 목록이 다른 창에 가려지거나 닫혀 있어도, 학생이 지금 보고 있는 대화창에서 바로 목록을 불러내 목표 대화로 돌아갈 수 있을까?

| 대안 | 대응 원인·인지적 한계 | 새 부담 | 검증 |
|---|---|---|---|
| A 목록·내용 통합 창 | 근접 부합성, 가림 | 창 관리 구조와 기존 사용 방식의 큰 변화, 동시 비교 불편 | 두 조건에서 전체 복귀 과업 비교 |
| B 대화창 상단 '대화목록' 버튼 | 실행차·기억 의존, 가림(목록만 전면 표시) | 모든 대화창에 버튼·목록 상태 처리. 창 개요 단계와 창끼리의 겹침은 남음 | 첫 발견, 목록 표시·상대 선택, 회귀 불편 |
| C 개별 창 식별 강화 | 유사성(창 개요·겹친 창) | 가려지거나 닫힌 목록 문제는 그대로 | 같은 창 수·가림에서 상대 탐지 비교 |
| D 기존 Dock 메뉴 경로 안내 | 기억 의존 | 화면 밖 메뉴 조작은 남음, 안내 기억 부담 | 안내 전후와 B 비교, 학습 효과 구분 |

현재 선택은 B, 보조안은 C다. 불편 당시 목록이 이미 열려 있었으므로 가려진 기존 목록을 현재 대화창에서 앞으로 불러내는 것이 확인된 문제에 가장 직접 대응한다. 효과·실현 가능성·새 부담·검증 가능성을 기준으로 한 판단이며 A보다 실측 성능이 좋다는 결론은 아니다. WhatsApp·Discord 비교는 work/q3/pc-ui-comparison.md에 있으며 Dock 동작·성능 추정에는 쓰지 않는다.

## 4단계 프로토타입

1. 모든 대화창 상단의 같은 위치에 문자 버튼 '대화목록'을 둔다. Chats에 해당하는 대화 목록을 연다.
2. 목록이 열려 있으나 가려져 있으면 그 목록 하나만 전면에 표시하고, 닫혀 있으면 복원한다. 중복 목록을 만들지 않는다.
3. 목록에서 상대를 고르면 그 상대의 대화창이 앞으로 오고, 상단 이름으로 목표인지 확인한다. 목록의 현재 대화 항목은 '현재 대화', 나머지는 '이 대화로 이동'으로 표시한다. 조작 결과를 즉시 보여 평가차를 만들지 않으려는 요구다(「8장 콘트롤 보충.pdf」 p.4).
4. 대화창을 닫거나 나가지 않게 한다. Dock 메뉴 등 기존 경로는 유지한다.

모형: work/q3/kakao-list-return.html. 한 화면 안의 모의 데스크톱에 다른 앱 창(예시) 1개, 대화목록 창 1개, 대화창 3개를 겹쳐 두고 창의 앞뒤 순서를 바꾼다. 처음에는 목록이 열려 있으나 다른 창 뒤에 가려져 있다. 어느 대화창의 '대화목록' 버튼을 눌러도 목록 하나만 앞으로 오고, 닫힌 경우에는 복원된다. 목록에서 상대를 고르면 그 대화창이 앞으로 오고 목록은 열린 채 뒤에 남는다. 창을 누르면 그 창이 앞으로 오며, 대화창별 초안은 각 창에 남는다. '목록이 가려진 상태로'·'목록을 닫은 상태로'는 시연용 모형 조작이며 제안 기능이 아니다.

그림: output/q3-list-return-prototype.png. ① 가려진 상태 → ② 버튼으로 목록을 앞으로 → ③ 상대 선택의 세 장면을 모형의 장면 지정(#scene=occluded, list-front, selected)으로 렌더링했다. 그림 원본은 work/q3/q3-list-return-figure.html과 q3-list-return-figure-model.html(모형 복사본에서 캡션·조작 버튼만 숨김)이다.

실제 카카오톡·macOS의 창 전면화·Dock 제어는 구현하지 않았고, 창 배치와 다른 앱 창은 예시다. 이전 A 모형은 work/q3/kakao-return.html 및 output/q3-prototype.png로 남긴다.

## 5단계 테스트 계획

미수행 계획이다. 시험지 PDF p.9는 5단계를 명시하나 답안 칸은 p.11의 프로토타입까지다. 추가 공지로 실수행을 요구한다면 확인한다.

- 과업: 창 개요에서 시작해 지시받은 상대의 대화를 열고 이름을 확인한다.
- 조건: 목록이 열려 있으나 가려진 상태(불편 장면), 닫힌 상태(확장). 기존 조건에서는 목록 선택·Dock 메뉴·창 닫기 등 모든 경로를 허용한다.
- 통제: 다른 앱·대화의 수, 상대 정보, 창 크기·가림, 해상도를 조건 간 맞춘다.
- 지표: 완료 여부, 전체 시간, 잘못된 상대 선택, 목록을 찾기까지의 행동·도움 요청. 닫은 창 수는 보조 지표다.
- 발견 가능성: 버튼을 안내하지 않은 첫 탐색은 참가자당 한 번만 측정되므로 참가자 간 비교가 필요하다. 사용자 본인은 Dock 경로와 B의 의도를 알고 있어 첫 발견 측정 대상이 될 수 없다.
- 현재 모형으로는 전체 복귀 시간을 비교할 수 없어, 같은 충실도의 기존 경로 모형을 준비하기 전에는 버튼 발견·목록 표시·상대 선택의 형성 평가만 가능하다.

방법 근거는 「2장 보충 인간공학 연구방법론.pdf」 PDF p.22-23, 32, 사용성 지표는 「Lecture 1 인간공학 소개 2026.pdf」 PDF p.51, 53이다.

## 남은 확인

목록을 가린 창의 종류, 불편 당시 화면(창 개요 캡처가 그 시점인지), 대화창 메뉴·메뉴 막대·단축키의 목록 열기 기능, Show All Windows의 동작, 앱·OS 버전, 답안 칸 크기, 실제 사용자 평가는 확인 필요다. 두 번째 후속 답변의 '대화창'이 대화 목록 창이라는 해석도 재확인하지 않았다.
