## 문제 정의

문제는 '창을 닫아야 대화에 접근할 수 있음'이 아니다. 목표 대화로 돌아가는 데 쓸 수 있는 대화 목록이 이미 열려 있었는데도 다른 창에 가려져 보이지 않았고, 사용자는 목록 대신 창을 하나씩 닫으며 찾는 우회로를 택했다. 즉 **열려 있는 진입점이 가려져 쓰이지 못하는 것**이 핵심이다. 목록이 아예 닫힌 경우 Dock 메뉴로 복원해야 하는 것은 후속 확인에서 드러난 같은 문제의 확장 조건으로 다룬다.

단일 과업은 학습 중 목표 대화로 복귀하는 것이다. 채널·광고 분류 문제는 묶지 않는다.

## 강의 원리와 원인 가설

1. 실행차와 머릿속 지식: 8장 PDF p.4는 실행차를 "사용자가 달성하고자 하는 목적과 시스템 이미지에 현재 나와있는 기능 또는 정보의 차이"로 정의한다. 목표는 다른 상대의 대화를 찾는 것인데, 그 기능을 하는 목록이 가려져 현재 화면에 나와 있지 않았다. 목록이 열려 있다는 사실과 위치를 사용자가 머릿속 지식으로 떠올려야 쓸 수 있는 상태다(「2026 4장 보충.pdf」 PDF p.34의 머리와 세상의 지식, p.53의 회상과 재인). 목록이 닫힌 경우에는 Dock 우클릭 절차까지 알아야 한다. 대화창의 ≡ 메뉴·메뉴 막대·단축키에 목록을 여는 항목이 있는지는 확인 필요다. 있다면 문제는 '경로 없음'이 아니라 '발견 가능성'이다. 사용자가 망각했거나 잘못된 심성모형을 가졌다고 단정하지 않는다.
2. 가림과 시각 탐색: 목록 창과 대화창의 이름·프로필이 다른 창에 가려지면 목표를 찾는 데 필요한 정보가 시야에서 사라진다. 후속 재현 화면에서 목록 창 일부와 뒤쪽 대화의 이름·프로필이 가려진 것을 확인할 수 있다. 선택적 주의와 시각 탐색(「3장 보충 2026.pdf」 PDF p.83, 95, 97)의 대상은 보이는 정보에 한정되므로, 가려진 목록은 탐색 후보에서 빠질 수 있다. 탐색 시간·시선은 미측정이다.
3. 창 개요에서의 유사성: 창 개요 캡처에서 카카오톡 대화창들은 작은 썸네일로 줄어들어 같은 연한 파란 배경과 같은 배치가 두드러지고, 구별의 주된 단서인 상대 이름은 이 크기에서 읽기 어렵다. 같은 외형의 항목은 유사성 원리에 따라 묶음으로 지각되기 쉽고(「3장 보충 2026.pdf」 PDF p.71, 101), 묶음 안에서 특정 창을 구별하려면 세부를 보는 초점 처리가 필요하다(같은 자료 PDF p.89). 기억 인출 측면에서도 유사성은 재인 실패(혼동)의 원인으로 제시된다(「2026 4장 보충.pdf」 PDF p.53, Memory Retrieval and Forgetting 항목). 실제 크기의 대화창에는 인원수, 프로필 이미지, 배너 같은 다른 단서도 보이므로 이 진단은 창 개요 장면에 한정한다. 캡처가 불편 시점의 화면인지와 오선택 횟수는 확인되지 않았다.
4. 근접 부합성(보조 진단): 6장 PDF p.32는 처리 근접성을 "한 작업에 함께 쓰는가"로 정의하고 "비교·통합, 하나의 판단"을 예로 든다. 목록에서 상대를 고르고 대화창에서 이름을 확인하는 것은 같은 과업에 쓰이지만 동시 비교·통합보다 순차 이동에 가깝다. 따라서 목록과 대화가 별도 창으로 분리되어 서로 가릴 수 있다는 점을 근접 부합성과 관련된 보조 진단으로만 쓰고, 이 원리에 직접 대응하는 대안은 A(통합 창)로 본다. 탐색 목록에 적용한 것은 해석적 확장이다.
5. 평가차(설계 기준 중심): 8장 PDF p.4는 평가차를 "실행을 한 다음에 그 결과가 사용자의 목적과 얼마나 차이"로 정의한다. 창을 하나씩 닫는 방식에서는 닫을 때마다 앞에 남은 창이 목표인지 다시 확인해야 했을 것으로 추정된다. 사용자가 그 판단이 어려웠다고 말하지는 않았고 판단 시간도 기록되지 않았으므로 원인으로 단정하지 않는다. 대신 선택안의 설계 기준으로 쓴다. 버튼을 누른 결과(목록이 앞에 나타남)와 상대를 고른 결과(맞는 대화가 앞에 옴)가 즉시 보여야 새 조작이 평가차를 만들지 않는다.

원문은 PDF 추출로 확인했고, 그림 중심인 6장 p.32와 3장 p.71은 렌더링해 확인했다. 효과는 검증하지 않았다.

## 대안의 재평가

| 대안 | 대응 원인·인지적 한계 | 비용·새 부담 | 판단 |
|---|---|---|---|
| A 목록·내용 통합 창 | 근접 부합성, 가림(목록이 내용과 한 창에 있어 따로 가려지지 않음) | 창 관리 구조와 기존 사용 습관의 큰 변화, 동시 비교 불편 | 장기 대안 |
| B 대화창의 '대화목록' 버튼 | 실행차·기억 의존(가려진 목록을 현재 화면의 버튼으로 불러냄), 가림(목록만 전면 표시) | 모든 대화창에 버튼과 목록 상태 처리 필요. 창 개요 단계와 창들끼리의 겹침은 남음 | 선택 |
| C 개별 창 식별 강화 | 유사성(창 개요·겹친 창에서 상대 이름·프로필을 크게) | 목록이 가려지거나 닫힌 문제는 그대로 | B의 보조안 |
| D 기존 Dock 메뉴 경로 안내 | 기억 의존(경로를 알려 줌) | 화면 밖 메뉴로 이동하는 조작은 남음 | 비교 기준 |

선택은 B다. 불편 당시 목록이 이미 열려 있었으므로, 새 목록 구조를 만드는 것보다 **가려진 기존 목록을 현재 대화창에서 바로 앞으로 불러내는 것**이 확인된 문제에 가장 직접 대응한다. 목록이 닫힌 경우에도 같은 버튼으로 복원할 수 있다. 창 개요 단계의 유사성은 B가 다루지 못하므로 C를 보조안으로 둔다. 효과·실현 가능성·새 부담·검증 가능성을 기준으로 한 설계 판단이며 A보다 성능이 우수하다는 실험 결과는 아니다.

## 선택안의 동작 요구

- 모든 대화창 상단의 같은 위치에 문자 버튼 '대화목록'을 둔다. Chats에 해당하는 대화 목록을 연다.
- 목록이 열려 있으나 가려져 있으면 그 목록 하나만 전면에 표시하고, 닫혀 있으면 복원한다. 누를 때마다 목록 창을 중복 생성하지 않는다.
- 목록에서 상대를 고르면 그 상대의 대화창이 앞으로 오고, 상단 이름으로 목표인지 확인한다. 목록 선택이 작동한다는 사용자 확인에 근거하며, 버튼에서의 연결은 구현 요구다.
- 피드백: 목록에서 현재 대화 항목은 '현재 대화', 나머지는 '이 대화로 이동'으로 표시한다.
- 대화창을 닫거나 나가게 하지 않는다. Dock 메뉴 등 기존 경로는 유지한다.
- 모형 범위: work/q3/kakao-list-return.html은 모의 데스크톱에서 겹친 창들의 앞뒤 순서를 바꿔, 가려진 목록을 버튼으로 앞으로 가져오기, 닫힌 목록 복원, 반복 누름 시 중복 없음, 상대 선택 시 해당 대화창 전면 표시를 보여 준다. 실제 카카오톡·OS 전면화·Dock 동작은 구현하지 않았고, 창 배치와 다른 앱 창은 예시다.

## 평가 범위

과업은 창 개요에서 시작해 지시받은 상대의 대화를 열고 이름을 확인하는 것이다. 조건은 목록이 열려 있으나 가려진 상태(불편 장면)와 닫힌 상태(확장 조건)로 둔다. 기존 조건에서는 목록 선택, Dock 메뉴, 창 닫기 등 참가자가 쓰는 모든 경로를 허용한다. 버튼을 안내하지 않은 첫 탐색은 참가자당 한 번만 측정되므로 참가자 간 비교가 필요하다. 사용자 본인은 Dock 경로와 B의 의도를 알고 있어 첫 발견 측정 대상이 될 수 없다. 현재 모형으로는 전체 복귀 시간을 비교할 수 없어, 같은 충실도의 기존 경로 모형을 준비하기 전에는 버튼 발견·목록 표시·상대 선택의 형성 평가만 제안한다. 모든 평가는 미수행이다.
