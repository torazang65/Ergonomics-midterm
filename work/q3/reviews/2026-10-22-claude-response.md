# Q3 답안 초안 비판 검토 (Claude CLI 별도 세션)

**확인 범위:** 이 환경에는 PDF 렌더링 도구(pdftoppm)가 없어 강의 PDF 원본을 열지 못했습니다. 시험지는 `sources/text/exam.md` 추출본으로만 봤습니다. 그래서 2번 질문에서 강의 정의와 맞는지 판단한 부분은 초안·`work/q3/followup-analysis.md`가 옮겨 적은 정의와 표준 교재 개념에 기댄 것이고, **원문 대조는 하지 못했습니다(확인 필요).** 이미지 5장과 HTML 모형은 직접 확인했습니다.

## 전체 판정: **보완 후 가능**

주제를 다시 고를 필요는 없습니다. 다만 실제로 겪은 불편과 선정한 문제가 어긋나 있습니다(지적 1). 모형과 본문의 동작 설명도 서로 다릅니다(지적 2). 이 두 가지는 제출 전에 반드시 고쳐야 합니다.

## 중요도순 지적

### 1. 실제 겪은 불편과 선정 문제가 어긋남 (1·2단계 전체)
- **위치:** 2단계 선정 문장("목록 상태에 따라 탐색 진입점을 다시 찾아야 하는 부담"), 원인 1·2행, 3단계 B 선택 이유("추가 자료에서 확인한 목록 복원 진입점에 직접 대응").
- **근거:**
  - 10월 22일 자기보고(`work/q3/user-followup.md` 20행)는 "창 개요에서 못 찾음 → Dock에서 열음 → 창 4개가 한꺼번에 뜸 → 하나씩 닫으며 찾음"이 전부입니다. 목록이 닫혀 있었다거나 Dock 우클릭을 썼다는 말은 없습니다.
  - 후속 메시지(`2026-10-22-followup-message.txt` 5행)는 "4개의 창이 열려 있다고 가정할 때 첫 번째 이미지처럼"이라고 했습니다. 첫 이미지의 네 창은 **목록 1개와 대화 3개**입니다.
  - `Kakaotalk Reference.png`의 빨간 점선 안에도 'Chats' 목록 창 썸네일이 보입니다. 다만 이 캡처가 실제 불편을 겪은 시점의 화면인지는 확인되지 않았습니다.
  - 따라서 **실제 불편은 목록이 열려 있는 상태에서 일어났을 가능성이 있습니다.** 그렇다면 핵심은 "목록이 열려 있었는데 왜 쓰지 않고 창을 닫았는가"입니다. Dock 우클릭 경로는 후속 확인에서 나온 일반적 사용법이지, 불편을 겪은 장면이 아닙니다.
- **수정안:**
  - 사용자에게 "당시 목록 창이 열려 있었는지, 목록을 쓰지 않은 이유가 무엇인지"를 확인하세요. 답을 얻기 전에는 '확인 필요'로 적습니다.
  - 문제 정의를 넓히는 예시: "학습 중 목표 대화로 돌아갈 때 대화 목록이라는 진입점이 **가려져 있거나 닫혀 있어** 바로 쓰이지 못하고, 사용자가 개별 창을 직접 구별하거나 닫는 우회로를 택하게 되는 부담."
  - 1단계에서 Dock 경로는 "후속 확인에서 드러난 목록 복원 방법"으로 표시해, 최초 장면과 구분하세요.

### 2. 모형(HTML·PNG)과 4단계 본문의 동작 모델이 다름
- **위치:** 4단계 2번("이미 열린 해당 대화창을 앞으로 가져온다"), 4번("상대를 고르면 대화창 상단 이름이 바뀐다"), 3번("작성 중인 초안도 유지"), 54행("모형은 … 목록 복원·상대 선택을 표현").
- **근거:**
  - `work/q3/kakao-list-return.html` 80–84행과 91행을 보면, 모형은 대화창 **하나**의 이름·메시지·초안을 상대별로 **바꿔 끼웁니다.**
  - 상대를 선택하면 목록이 자동으로 닫힙니다(91행 `state.listOpen=false`).
  - 겹친 여러 대화창, 다른 창에 가려진 목록을 전면에 띄우는 동작, 목록 중복 생성 방지는 모형에 없습니다.
  - 즉 모형은 한 창 안에서 대화를 전환하는 A안에 가까운 방식입니다. 2번(별도 창을 앞으로)과 4번(같은 창의 이름이 바뀜)도 서로 다른 모델을 설명하고 있습니다.
  - PNG 하단의 "닫혀 있어도 같은 버튼으로 복원 / 이미 열려 있으면 같은 목록 표시"는 정지 이미지 한 장(목록이 열린 상태)으로는 보이지 않습니다.
- **수정안:**
  - 4번을 "상대를 고르면 그 상대의 대화창이 앞으로 오고, 상단 이름으로 목표인지 확인한다"로 바꿔 2번과 맞추세요.
  - 54행에 한계를 명시하세요. 예: "모형은 창 전면화를 한 창의 내용 교체로 단순화했고, 가려진 목록의 전면 표시와 여러 창이 겹친 상태는 표현하지 않았다. 선택하면 목록이 닫히는 것은 모형의 단순화다."
  - 3번의 '초안 유지'는 별도 창 모델에서는 당연한 성질이므로 지우거나, 모형상의 요구로 한정하세요.

### 3. 근접 부합성(원인 3행)은 무리한 확장
- **위치:** 2단계 3행 전체, 4단계 54행 "표시 근접성을 높이고".
- **근거:** 6장 PDF p.32는 원문을 확인하지 못했습니다. 아래 판단은 초안이 옮긴 정의(처리 근접성과 표시 근접성의 일치·불일치 표)를 기준으로 합니다.
  1. **처리 근접성 '높음'은 근거가 약합니다.** 목록에서 고른 뒤 대화창에 쓰는 것은 **순차적인 이동**입니다. 두 정보를 동시에 비교하거나 통합하는 처리가 아닙니다. 슬라이드 예시(값 비교, 조작 버튼 배치)와 성격이 다릅니다.
  2. **표시 근접성 '낮음'은 이미지와 어긋납니다.** `followup-list-open.png`에서 목록 창은 대화창 바로 왼쪽에 붙어 있고, 일부가 가려져 있을 뿐입니다. 실제 문제는 거리보다 **가림**이며, 이는 5행이 이미 다룹니다. 목록이 닫힌 경우는 표시가 '멀리' 있는 것이 아니라 **아예 표시되지 않는 것**입니다. 이는 실행차와 머릿속 지식의 문제(1·2행)입니다. 또 Dock은 '화면 밖'이 아니라 화면 가장자리에 있고, 메뉴가 숨겨져 있을 뿐입니다.
  3. **'따로 처리하는데 가까이 배치' 해석은 지우는 것이 좋습니다.** 다른 대화창의 위치는 사용자가 배치한 결과입니다. 시스템이 설계한 디스플레이 배치로 진단하기 어렵습니다.
  4. B 버튼은 표시물을 옮기는 것이 아니라 **조작기를 추가**하는 것입니다. 그래서 "B가 표시 근접성을 높인다"는 효과 주장은 성립하기 어렵습니다. 초안도 54행에서 "근접성을 가장 크게 높이는 것은 A안"이라고 인정합니다.
- **수정안:** 3행을 지우거나, 한 줄짜리 보조 진단으로 줄이세요. 예: "목록을 볼 때와 대화를 확인할 때 서로 다른 창을 오가야 한다는 점은 근접 부합성과 관련된다. 다만 순차 이동에 적용한 것은 해석적 확장이고, 직접 해결하는 대안은 A이다." 4단계의 근접성 효과 문장은 지우세요. 시험지 p.10이 근접 부합성을 예로 들었다고 해서 반드시 써야 하는 것은 아닙니다(추출본 기준).

### 4. 유사성 혼동(원인 4행): 이미지와 어긋나는 단정이 있고, 이미지 선택도 틀림
- **위치:** "상대를 구별할 단서는 상단의 이름·프로필 영역뿐이다", "캡처에서".
- **근거:**
  - `followup-list-open.png`의 대화창에는 이름 말고도 구별 단서가 보입니다. 참여자 수(67, 1749), 각기 다른 프로필 이미지, KULL 창의 경고 배너와 붉은 포스터 이미지가 있습니다.
  - 보이는 세 창은 모두 단체방이거나 이름만 보이는 방입니다. 실제 목표였던 '친구' 1:1 대화창은 이미지에 없습니다.
  - 유사성이 가장 크게 작용할 장면은 **창 개요(Mission Control)**입니다. `Kakaotalk Reference.png`에서 카카오톡 창들은 작은 썸네일로 줄어들어 이름을 읽기 어렵고, 같은 연한 파란 배경과 같은 배치만 두드러집니다. 이것이 최초 실패 단계(창 개요에서 못 찾음)와 직접 연결됩니다. 그런데 초안 2단계는 이 장면을 진단하지 않습니다.
  - 3장 PDF p.71·89·101과 4장 PDF p.53의 연결은 원문을 확인하지 못했습니다. 초안이 쓴 정의(유사성으로 묶여 보임, 초점 처리, 유사성으로 인한 재인 실패)가 맞다면 연결 자체는 원문 범위 안입니다. 다만 4장 p.53의 '재인 실패'는 **기억에서 꺼내는 과정**의 개념입니다. 화면에서 지각적으로 구별하지 못하는 것과는 다르므로 "기억 측면에서도"라고 범위를 표시해야 합니다.
- **수정안:** "창 개요 캡처(`Kakaotalk Reference.png`)에서 카카오톡 대화창들은 작은 크기로 같은 배경색·배치를 공유해 서로 비슷하게 보이고, 구별의 주된 단서인 이름은 이 크기에서 읽기 어렵다. 이 캡처가 실제 불편을 겪은 시점의 화면인지는 확인 필요." '뿐이다'는 '주된 단서'로 바꾸세요.

### 5. 평가차(원인 6행)는 자기보고로 부분적으로만 뒷받침됨
- **위치:** "닫을 때마다 … 다시 판단해야 했다. … 평가차가 매번 생기며".
- **근거:**
  - 자기보고는 "하나씩 닫아가며 원하는 친구의 창을 찾음"입니다. 그래서 '닫을 때마다 앞에 남은 창을 확인했다'는 추론은 합리적입니다.
  - 하지만 사용자가 그 판단이 **어려웠다고** 말한 적은 없습니다. 평가차는 시스템 상태를 해석하기 어려울 때 생기는 간극입니다. 이름이 보이는 창을 하나씩 확인하는 것은 순차적인 시각 탐색에 가깝습니다.
  - 초안도 "했다"는 단정형을 쓰면서, 바로 다음 문장에서는 "생기며"라고 사실처럼 이어 갑니다.
  - 제안한 B안에서도 4번에서 이름 확인이 여전히 필요합니다. 그래서 "평가차를 줄인다"는 효과는 이 행에서 직접 이어지지 않습니다.
- **수정안:** 6행을 "닫을 때마다 남은 창이 목표인지 다시 확인하는 반복 판단이 필요했을 것으로 추정된다(판단 난이도·시간은 미기록). 이는 평가차와 관련될 수 있는 가설이다"로 약하게 쓰세요. 또는 원인 행에서 빼고 4단계의 **설계 기준**(조작 결과가 즉시 보이게 함)으로만 쓰세요. 8장 PDF p.4 원문은 확인하지 못했습니다.

### 6. "목록 복원 경로가 드러나지 않음"을 사실처럼 씀 (원인 1행)
- **근거:**

  - 사용자는 Dock 경로를 이미 알고 있으므로, **이 사용자에게** 실행차가 크다는 근거도 약합니다.
- **수정안:**

  - 1행과 2행은 둘 다 "화면에 단서가 없어 지식이 필요하다"는 같은 원인입니다. 하나로 합치면 분량도 줄어듭니다.

### 7. 3단계: 대안과 원인의 연결, 인지적 한계 표시가 없음
- **근거:**
  - 시험지 p.10은 "인지적 한계를 극복할 수 있는 … 아이디어"를 요구합니다(추출본 기준). 그런데 표에는 각 대안이 어떤 원인·인지적 한계에 대응하는지 나타내는 칸이 없습니다.
  - `process.md` 54행에 있는 대응 관계(A↔근접성, C↔유사성, D↔기억 의존)가 답안에는 빠졌습니다.
  - B는 지적 4의 창 개요 단계와 5행(가림 상태에서 창을 직접 고르는 경우)에 대응하지 않습니다. 이 부분은 C가 맡습니다.

- **수정안:** 표에 '대응 원인' 칸을 추가하세요. 그리고 B 선택 이유에 "창 개요·가림 단계는 B가 다루지 못하므로 C를 보조안으로 둔다(또는 B+C)"를 한 줄 넣으세요.

### 8. 1단계에서 빠진 근거와 페르소나·페인 포인트 표현
- **페인 포인트 표현:** 분석가의 언어("진입점이 달라진다")로 되어 있습니다. 사용자가 실제로 겪은 일("원하는 친구의 창을 바로 찾지 못해 창을 하나씩 닫아야 했다")을 먼저 쓰세요.
