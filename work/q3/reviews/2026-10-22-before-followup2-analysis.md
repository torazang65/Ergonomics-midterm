# 목록 창의 상태에 따른 대화 복귀 경로 분석

## 새로 확보한 근거

후속 설명과 세 이미지는 목록 창의 상태에 따라 대화 탐색 진입점이 달라진다는 분석을 뒷받침한다. 목록이 열려 있을 때는 기존 목록 선택으로 다른 대화창을 닫지 않고 접근할 수 있다는 사용자 확인이 가장 중요한 변경 근거다.

## 문제 정의의 수정

문제는 '창을 닫아야 대화에 접근할 수 있음'이 아니다. 과제 질문을 위해 대화를 찾아 돌아가려는 목표에서, 목록이 열려 있으면 목록 선택으로 접근하지만 닫혀 있으면 별도 목록 복원 경로를 찾아 실행해야 한다. 동시에 열린 대화창의 가림은 목록 경로를 사용하지 않을 때 개별 창 식별에 부담을 줄 수 있다.

단일 과업은 학습 중 목표 대화로 복귀하는 것이다. 목록 상태와 다중 창은 이 과업의 조건으로 다룬다. 채널·광고 분류 문제를 추가로 묶지 않는다.

## 강의 원리와 원인 가설

1. 실행차: 목표는 다른 상대의 대화를 찾는 것인데, 목록이 닫힌 현재 대화 화면에서는 목록 복원 경로가 뚜렷하게 드러나지 않는다. 사용자가 확인한 경로는 Dock의 문맥 메뉴다. 목표와 현재 화면에 제시된 조작 정보 사이의 거리를 줄이는 설계가 적절하다. 「8장 콘트롤 보충.pdf」 PDF p.4의 실행차 정의를 적용한다. '사용자의 잘못된 심성모형'이나 '우클릭 기능을 전혀 몰랐다'는 사실은 추가하지 않는다.
2. 머릿속 지식과 화면의 단서: Dock 우클릭 후 Chats를 선택하는 절차를 알고 있어야 그 경로를 이용할 수 있다. 현재 대화 화면에 '대화목록'이라는 의미 있는 제어를 드러내면 경로 기억에 덜 의존하고 보이는 단서에서 선택하도록 지원할 수 있다는 가설이다. 사용자가 실제로 망각했다는 주장은 아니다. 「2026 4장 보충.pdf」 PDF p.34, 53.
3. 근접 부합성: 목표 대화로 돌아가는 한 과업에서는 대화 목록(누구에게 갈지 고르기)과 대화창(이름 확인·질문 작성)을 함께 써야 한다. 즉 처리 근접성이 높다. 그런데 목록이 열려 있어도 별도 창으로 대화창들과 겹쳐 있고, 닫혀 있으면 확인된 진입점은 대화 화면 밖의 Dock 문맥 메뉴에 있다. 표시 근접성이 낮다. 강의 표의 '함께 처리 + 떨어뜨려 배치 → 불일치(눈이 오가며 비교)' 칸에 해당한다는 진단이다. 반대로 지금 과업과 무관한 다른 대화창들은 따로 처리되는 정보인데 같은 영역에 겹쳐 놓여 있다. 이는 '따로 처리 + 가까이 배치 → 불일치(섞여서 헷갈림)' 칸으로 해석할 수 있다. 「6장 디스플레이 보충 2026.pdf」 PDF p.32. 슬라이드의 예시는 두 값의 비교·통합과 조작 버튼·작동 부위의 배치이므로, 탐색 목록과 내용의 관계에 적용한 것은 이 원리의 해석적 확장이다. 시선 이동량이나 비교 시간은 측정하지 않았다.
4. 유사성에 의한 혼동: 창 개요 캡처(Kakaotalk Reference.png)와 목록 닫힘 캡처에서 카카오톡 대화창들은 같은 연한 파란 배경, 같은 상단 아이콘 배치, 같은 말풍선·입력 영역 구성을 공유한다. 상대를 구별하는 단서는 상단의 이름·프로필 영역에 집중되어 있고, 겹친 창에서는 그 영역이 가려지기도 한다. 같은 외형의 항목은 유사성 원리에 따라 하나의 묶음으로 지각되기 쉽고(「3장 보충 2026.pdf」 PDF p.71, 101), 묶음 안의 개별 창을 구별하려면 세부를 보는 초점 처리가 필요하다(같은 자료 PDF p.89). 기억 인출 측면에서도 유사성은 재인 실패(혼동)의 원인으로 제시된다(「2026 4장 보충.pdf」 PDF p.53). 이는 사용자가 '원하는 상대의 창을 고르기 어려웠다'는 자기보고에 대한 원인 가설이다. 실제로 잘못 고른 횟수나 혼동 사례는 기록되지 않았다.
5. 시각 탐색과 가림: 겹친 대화창 일부의 이름·프로필이 가려진 화면은 개별 창을 직접 골라야 할 때의 식별 문제를 뒷받침한다. 기존 목록은 대안 경로로 이미 작동한다. 「3장 보충 2026.pdf」 PDF p.83, 95, 97. 탐색 시간·시선·인지 부하는 미측정이다.
6. 평가차: 8장 p.4는 실행 뒤 결과가 목적과 얼마나 차이 나는지를 평가차로 정의한다. 최초 경험에서 사용자는 창을 하나씩 닫았다고 보고했다. 이 방식에서는 닫을 때마다 앞에 남은 창이 목표 상대인지를 이름으로 다시 판단해야 하고, 위의 유사성·가림이 이 판단을 어렵게 할 수 있다. 다만 판단에 걸린 시간이나 잘못 판단한 일은 기록되지 않았으므로 이 연결은 가설이다. 이 원리는 선택안의 설계 기준으로도 쓴다. 버튼을 누른 뒤 목록이 전면에 나타났는지, 상대를 고른 뒤 맞는 대화가 앞에 왔는지가 즉시 보여야 새 버튼이 평가차를 만들지 않는다. 「8장 콘트롤 보충.pdf」 PDF p.4.

위 PDF의 관련 페이지를 원문 추출로 확인했고, 6장 p.32와 3장 p.71은 그림 중심이라 페이지를 렌더링해 표의 칸 구성과 예시 그림도 확인했다. 실행차·평가차가 줄었다거나 기억 부담·혼동이 실제로 감소했다는 효과는 아직 검증하지 않았다.

## 대안의 재평가

| 대안 | 이번 근거에 대한 대응 | 비용·새 부담 | 판단 |
|---|---|---|---|
| A 통합 대화 모드 | 목록과 내용을 같은 창에 두어 탐색 진입점을 유지 | 창 관리 구조 수정, 동시 비교·기존 사용 습관 변화, 목록 닫힘 방지 요구 | 장기 대안으로 유지. 유일한 해법이나 현재 최선으로 확정하지 않음 |
| B 각 대화창에 대화목록 버튼 | 현재 대화에서 기존 목록을 복원·전면 표시해 이미 작동하는 목록 선택 경로에 연결 | 모든 대화창에 버튼 공간과 목록 상태 처리 필요. 창 겹침 자체는 남음 | 선택할 프로토타입. 이번 확인으로 드러난 경로 문제에 직접 대응 |
| C 제목·프로필 식별 강화 | 목록 대신 개별 창을 고를 때 구별을 도움 | 목록이 닫힌 상태의 복원 경로는 그대로임 | 보조 대안 |
| D 기존 Dock 메뉴 경로 안내 | 기존 기능만으로 목록 복원 및 상대 선택 | 안내를 기억해야 하고 사용 중 화면에서 벗어나는 조작은 남음 | 비교 기준. 적은 변경으로 충분한지 확인 |

선택은 B다. 기존 목록 선택이 이미 작동한다는 강점을 사용하면서 목록 복원 진입점을 대화 화면에서 직접 제공하기 때문이다. 'A보다 실측 성능이 우수하다'는 결론은 아니다.

## 선택안의 동작 요구

- 모든 대화창 상단의 같은 위치에 문자 버튼 '대화목록' 배치. 친구 목록은 목적이 다르므로 이 버튼은 Chats에 해당하는 대화 목록을 연다.
- 목록이 닫혀 있으면 기존 대화 목록 창을 복원하고, 열려 있으나 가려져 있으면 그 목록 하나만 전면 표시한다. 누를 때마다 목록 창을 중복 생성하지 않는다.
- 목록에서 상대를 고르면 이미 열려 있는 해당 대화창을 앞으로 가져온다. 이 선택 접근은 기존 기능이 작동한다는 사용자 확인에 근거하며, 제안된 버튼에서의 연결은 구현 요구다.
- 평가차를 줄이는 피드백: 버튼을 누르면 목록이 전면에 나타나는 변화가 바로 보이고, 목록에는 현재 대화 항목이 '현재 대화'로 표시된다. 상대를 고르면 대화창 상단 이름이 바뀌어 목표 상대인지 확인할 수 있다. 현재 모형은 상단 이름 갱신과 목록의 '현재 대화'/'이 대화로 이동' 표시를 구현했다.
- 대화창을 닫거나 나가게 하지 않는다. 기존 대화·초안 상태를 유지한다. 목록을 다시 닫아도 대화창의 '대화목록' 버튼은 남긴다.
- Dock 우클릭 메뉴는 유지하고, 다른 창·단축키 등 기존 접근 경로도 테스트에서 허용한다.
- 모형은 버튼→목록 표시·복원→상대 선택을 같은 화면의 모의 창들로 표현한다. 실제 카카오톡 창·OS 전면화·Dock 동작은 구현하지 않는다.

## 평가 범위

목록이 열려 있는 조건과 닫힌 조건을 각각 비교한다. 기존 목록이 열린 조건에서는 기존 선택 경로를 사용하고, 닫힌 조건에서는 사용자가 확인한 Dock 우클릭 경로와 다른 확인된 경로를 허용한다. 새 버튼을 안내하지 않은 첫 탐색과 위치를 익힌 뒤의 사용을 구분하면 발견 가능성과 반복 사용 효율을 따로 볼 수 있다.

현재 제작할 버튼 모형만으로 기존 앱과 전체 수행 시간을 비교하지 않는다. 같은 충실도의 기존 경로 모형을 만들거나 실제 앱 수준 구현을 준비하기 전까지는 버튼 발견·목록 복원·상대 선택의 형성 평가만 제안한다. 전체 과업의 완료 여부·시간·오선택과 목록 복원까지의 행동을 기록하며 모든 결과는 미수행이다.
